Aegister Cloud Defender sits between your visitors and your site. Every request follows the same path:

![How It Works](/images/cloud-defender-how.png)

## The request path

1. **DNS:** your domain, for example **client1.domain1.com**, is a CNAME for **secure.aegister.com**,
   so visitors reach Cloud Defender instead of your server.
2. **Cloudflare:** the request enters through Cloudflare, which mitigates DDoS traffic and serves
   cached content. Cloudflare passes on the visitor's real address in the **CF-Connecting-IP**
   header.
3. **Google Cloud load balancer with Cloud Armor:** Cloud Armor accepts only traffic coming from
   Cloudflare and refuses everything else, so the protection cannot be bypassed by reaching
   Cloud Defender another way. Here the attack URL rule and attack detection run (see below).
4. **Aegister proxy:** refuses requests from addresses on the Threat Intelligence list, then
   forwards the rest to your server, using the visitor's real address from **CF-Connecting-IP**.
5. **Your site:** the requests that passed every check arrive at your server, with nothing for the
   visitor to notice.

Lock your server so that it accepts traffic only from Cloud Defender (step 4 of the
[activation guide](/documentation/en/cloud-defender/how-to-get-started)). Otherwise anyone who knows
its address can skip the whole path above.

## What each layer does

- **Threat Intelligence (blocks):** Aegister's threat-intelligence list holds addresses already seen
  attacking other targets and is updated continuously. A request from one of them is refused before
  it reaches your site.
- **Attack URL rule (blocks):** judges only the address and the headers of a
  request: requests for sensitive files such as `/.env` or `/.git`, path traversal, Log4Shell
  strings, malformed or abusive HTTP and scanning tools that declare themselves. It never reads form
  fields, JSON bodies or cookies, so your users' input is never judged by it.
- **Signature rules (blocking on request):** every request is checked against the OWASP Core Rule
  Set, which covers SQL injection, cross-site scripting and other attack patterns. Blocking is
  available on request, per site: Aegister turns it on when you ask. Until it is on, matches are
  recorded as anomalies and reviewed by Aegister's analysts.
- **Scanner detection (detection only):** request patterns typical of automated scanners, such as a
  high share of not-found pages or a walk through many paths, are recorded as anomalies. The
  detection looks at behaviour, never at the name a client gives itself.
- **Health checks:** Cloud Defender periodically checks that your domain and your server respond,
  and that requests to your site really pass through the protection. The result is shown on the
  status page.

## What you see

Every request Cloud Defender refuses is recorded with its time, source, request and the layer that
refused it, and stays available on the
[status page](/documentation/en/cloud-defender/reading-your-status-page).
